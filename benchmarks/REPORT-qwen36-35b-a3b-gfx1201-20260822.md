## Scope

Qwen3.6 is **additive**. Qwen3.8, Gemma 4 and every other manifest entry are
untouched, and the generic MoE machinery (`moe_offload`, `--n-cpu-moe`,
`--cpu-moe`, the semantic validators, the campaign runners) is reused rather than
duplicated — this campaign added no second MoE abstraction.

Out of scope, recorded as such rather than silently omitted:

- **Vision.** The model is multimodal upstream and the GGUF repository ships
  three `mmproj` files. None was downloaded, none is passed to `llama-server`,
  and `/props` reports `modalities: {vision:false, video:false, audio:false}`.
- **Context beyond 262144.** Upstream advertises an extension. It is not
  exposed here and was not tested.
- **MTP / speculative decoding.** Settled by the GGUF itself; see §4.

**The architecture identifier is not the marketing name.** The GGUF says
`qwen35moe`, not `qwen36`. Anything that keys on the family name rather than on
the header would look at the wrong table.

**Do not read this as a dense 35B.** Two consequences drive the whole campaign:

1. **Only 10 of 40 layers hold a KV cache.** The loader confirms it directly:
   `llama_kv_cache: size = 85.00 MiB (8192 cells, 10 layers, 1/1 seqs)`. The
   remaining 30 layers hold a fixed recurrent state — `62.81 MiB` for the whole
   model at any context, of which `R (f32) 2.81 MiB` is the convolution state
   and `S (f32) 60.00 MiB` the DeltaNet state.
2. **Expert FFN is 84.8% of the weights.** Placement, not `gpu_layers`, is the
   lever.

## 4. MTP and speculative decoding: settled by the header

**MEASURED, and it closes the question.** Every one of the seven GGUFs contains
**zero** MTP tensors and zero `nextn` tensors, against 733 total. Upstream
declares `mtp_num_hidden_layers: 1`, so the head exists in the checkpoint and was
dropped in conversion.

There is therefore nothing to A/B. Speculative decoding stays disabled, the
manifest declares no `spec_decoding` block, and the reason is a property of the
artifact rather than a performance judgement. Should Unsloth publish a build that
retains the head, the existing `spec_decoding` schema and the `blk.NN` quality
gate in `gguf_probe.py` already cover it — no new machinery is needed.

### 5.1 The classifier had to learn what a hybrid is

`tensor_category` in `gguf_probe.py` classified by name, and on a hybrid a name
cannot decide: the 30 recurrent blocks and the 10 attention blocks both call
their projections `attn_*`. Counting `blk.N.attn_qkv` as attention would have put
the largest tensors of 30 of 40 layers under a heading that implies a KV cache
they do not have.

The fix is structural rather than Qwen-specific: **a block that owns any `ssm_*`
tensor is a recurrent block, so its projections belong to the recurrent
operator.** It is a no-op on any model without recurrent tensors.

That was verified rather than asserted. `scripts/v2/eval/test_gguf_probe.py`
replays the Gemma 4 26B A4B censuses — the one committed by its campaign plus the
three local ones — through the current classifier and requires **zero**
classification changes across all 2632 tensors. Vision (`v.`/`mm.`/`mmproj`) and
MTP (`nextn`) names are asserted in the same test.

### 5.2 The UD quant mixes are not uniform across layers

**MEASURED**, from the loader's per-tensor placement log at `--n-cpu-moe 16`.
`UD-Q3_K_XL` layer 1 carries `q5_K` down-projection and `iq4_xs` gate/up (448
MiB of experts); layers 0 and 2–15 carry `iq4_xs` down and `iq3_xxs` gate/up (332
MiB). The mean of 340 MiB/layer in §5 therefore under-describes the first
layers, and `--n-cpu-moe N` does not move a constant amount per increment. This
is why the placement knee is measured rather than computed.

### 6.3 Three runtime findings that change how this model must be driven

**`tool_choice` must be a string on this build.** The OpenAI object form
`{"type":"function","function":{"name":"read_file"}}` is **not rejected** — the
server logs `Wrong type supplied for parameter 'tool_choice'. Expected 'string'`
and silently falls back to the default. HTTP 200, no error field, ordinary auto
selection. A harness that forces one specific function gets something else and
has no way to know. `tool_choice: "required"` works correctly.

**The chat parser is `peg-native`.** The template emits an XML tool-call syntax
(`<tool_call><function=name><parameter=k>value</parameter></function>`), not the
JSON form Qwen3.8 uses, and the question of whether llama.cpp turns that back
into structured `tool_calls` could not be answered from the template alone. It
does — see §6.4.

**mmap plus CPU tensor overrides is flagged by the runtime itself**:
`tensor overrides to CPU are used with mmap enabled - consider using --load-mode
none for better performance`. `--load-mode` is available on both `llama-server`
and `llama-bench`. It is a candidate lever, measured in §8.3.

The loader also emits `chat template supports preserving reasoning, consider
enabling it via --reasoning-preserve`. See §10.

**Read the `dedicated` and `shared` columns together, and the reason the sweep
exists becomes visible.** For Q3_K_XL, dedicated VRAM reads 15974, 15933, 15922,
15893 MiB at `ncpumoe` 0, 2, 4, 6 — it moves by 81 MiB across three steps and
says essentially nothing. Over the same three steps shared falls 3147 → 2491 →
1927 → 1278 MiB. The AMD driver does not fail an oversized allocation; it
satisfies what it can from dedicated and pages the rest over PCIe. Dedicated
therefore saturates near the card's size and stops tracking the configuration
exactly when the configuration is getting worse.

A selection rule written against dedicated VRAM alone would have picked
`ncpumoe: 0` for every quantization here. Every one of those cells is paging.

**`IQ4_XS` at `ncpumoe 0` is the clearest single case.** It loads. It reports
15902 MiB dedicated, which looks like a fit. It also holds **4042 MiB** of shared
memory — 3720 MiB above the idle baseline — and a **19.03 GiB** working set
against 10.11 GiB for the same weights at `ncpumoe 20`.

**Load time is not usable as a second signal here, and an earlier draft of this
section wrongly used it.** Each model's `ncpumoe 0` cell is the first time the
campaign touched that GGUF, so it is a cold read from disk and the 30.7 s it
took is not comparable to the 6.5 s of a later, cached cell. The cell that
settles it is `IQ4_XS` at `ncpumoe 2`: it holds 3346 MiB of shared memory —
nearly as much as `ncpumoe 0` — and loads warm in 10.6 s. Paging of that
magnitude costs approximately nothing at load, so the 30.7 s was the file read.
Load time in the tables above is reported as measured and should be read as a
disk-cache artefact, not as a property of the placement.

  floor, but dedicated is 15517 MiB, leaving **787 MiB**. It is healthy and it is
  not a workstation profile.
- `Q3_K_S` at `ncpumoe 6`: shared at the 423 MiB floor, headroom **519 MiB**.

Both are `elevated`, not `pressured` — the classifier is right about them and the
reserve is what rejects them. Neither test subsumes the other.

### 7.3 Full GPU residency is admissible for exactly one candidate

`UD-Q2_K_XL` at `ncpumoe 0` holds every expert on the card: 14516 MiB dedicated,
423 MiB shared, 1788 MiB headroom, `ok`. It is the only one of the four for
which full residency clears both gates.

Whether it is also the *fastest* Q2_K_XL configuration is a separate question
that this phase cannot answer, and the Qwen3.8 campaign found the opposite for
that model — full residency was worst on both axes. §8 measures it rather than
assuming either way.

### 7.4 Commit tracks VRAM, not host-resident weight

`docs/TUNING.md` §1.2 models commit as `VRAM + W_cpu + cache_ram + ~1.4 GiB`,
anchored on a 9B. That does not describe this model:

| Model | `ncpumoe` | marginal VRAM | commit | expert weight on host |
|---|---:|---:|---:|---:|
| Q3_K_XL | 12 | 11.99 GiB | 12.00 GiB | ~4.8 GiB |
| Q3_K_XL | 20 | 9.39 GiB | 9.40 GiB | ~8.0 GiB |
| IQ4_XS | 16 | 11.26 GiB | 11.26 GiB | ~6.4 GiB |

Commit equals marginal VRAM to within 10 MiB while several GiB of expert weight
sits on the host. The host-resident experts are **mmap'd and file-backed**, so
they are not private commit at all — llama.cpp reports them as `CPU_Mapped`, and
`--n-cpu-moe` does not add a commit term. Under this placement mechanism the
`+ W_cpu` term in the `docs/TUNING.md` §1.2 formula is zero.

**A caveat that matters for the manifest.** A load-only cell samples the working
set before inference has touched most of those mapped pages, so `WS` here is a
lower bound on steady-state residency for an offloaded configuration. The
`resources.peak_ram_gib` and `resources.peak_commit_gib` recorded for any
Qwen3.6 profile must come from a cell that actually generated tokens, not from
this table. §11 supplies them.

### 7.5 Repeatability, and why the marginal figure is the one to quote

Five configurations were measured twice, once in Phase 1 and again later, on
independent server starts. They are an accidental control — Phase 1 and the
budget search wrote different file names for the same cell — and a useful one.
Four of the five have neither reading spilling:

| Cell | marginal (a, b) | Δ | dedicated (a, b) | idle (a, b) |
|---|---|---:|---|---|
| IQ4_XS ctx32768 `n16` | 11528, 11510 | −0.16% | 14209, 14173 | 2681, 2663 |
| Q2_K_XL ctx32768 `n0` | 12041, 12023 | −0.15% | 14516, **14671** | 2476, **2648** |
| Q3_K_S ctx32768 `n8` | 12573, 12591 | +0.15% | 15174, 15232 | 2601, 2640 |
| Q3_K_XL ctx32768 `n12` | 12276, 12261 | −0.13% | 14756, **14925** | 2480, **2664** |

Marginal VRAM reproduces to within **0.16%**. Raw dedicated VRAM moves by up to
**169 MiB** between the same two runs, and the idle column shows why — the
desktop's own hold drifted by almost exactly the same amount. Subtracting the
idle baseline removes it.

This is the practical justification for the promotion policy's insistence on
recording the idle baseline. It also bounds how much of §7.1's `dedicated`
column can be read as signal: differences under ~200 MiB there are the desktop,
not the configuration.

**The fifth pair disagrees by 9.98%, and it belongs in this table rather than
outside it.** `Q3_K_S ctx32768 n6` read 13204.6 MiB at 14:51 and 12006.8 MiB at
17:48. That is not a repeatability failure; it is §7.1's inversion caught in the
act. The second reading is spilling **1284 MiB** into shared against the first's
100 MiB, and a spilling cell is charged *less* dedicated memory precisely
because part of its allocation went elsewhere. The lower number is the worse
configuration.

Which is the whole argument for the spill filter. Had the campaign averaged the
two, or preferred the smaller figure as the safer one, it would have concluded
that `n6` fits comfortably — when in fact that reading is the one that pages. A
repeatability control is only meaningful over cells that pass the shared test
first. All five pairs are in Appendix I.

### 8.1 Full GPU residency is optimal for Q2_K_XL — the opposite of Qwen3.8

`REPORT-qwen38-27b-gfx1201-20260821` §3 found that on Qwen3.8-27B full residency
was the *worst* configuration on both axes, beaten on decode by a 4-block CPU
split and on prefill by an 8-block one. That result does not carry over:

| Q2_K_XL | pp512 | change |
|---|---:|---|
| `ncpumoe 0` (everything on GPU) | 2324.34 | — |
| `ncpumoe 6` | 841.57 | **−64%** |

Moving six layers' experts to the host costs a factor of 2.8 in prefill. The
mechanism differs because the offload differs. Qwen3.8's `-ot` split moved dense
FFN tensors and *freed VRAM that the compute buffers then used*, lifting the
adapter off its occupancy cliff. Q2_K_XL at `ncpumoe 0` is not near that cliff —
§7.1 measures 89.0% occupancy and 423 MiB of shared memory, the desktop's own
floor — so there is no cliff to escape and the offload only adds host work.

**Full residency is therefore optimal exactly when it is admissible, and §7
found it admissible for only one of the four candidates.** Neither "keep it all
on the GPU" nor "always split" is the rule; the reserve and the pressure state
decide, and then more experts on the device is better.

### 8.2 Decode against the Qwen3.8 control

Same adapter, same runtime, same flags. Qwen3.8 figures from
`REPORT-qwen38-27b-q3-q2-kvq4-20260821` §8.

| Weights | Qwen3.8-27B (dense) | Qwen3.6-35B-A3B | ratio |
|---|---:|---:|---:|
| Q2_K_XL, pp512 | 561.43 | 2324.34 | **4.14×** |
| Q2_K_XL, pp32768 | 428.49 | 1541.89 | **3.60×** |
| Q2_K_XL, tg128 | 22.16 | 103.21 | **4.66×** |
| IQ4_XS, pp512 | 281.59 | 366.61 | 1.30× |
| IQ4_XS, pp8192 | 258.80 | 402.20 | 1.55× |
| IQ4_XS, tg128 | 16.04 | 40.95 | **2.55×** |

The Q2_K_XL comparison is not like-for-like on placement — Qwen3.6 is fully
resident here while Qwen3.8 carried a 4-block CPU split — but it is like-for-like
on *what the operator can actually run*, since §7 established that this
placement is admissible for these weights.

The IQ4_XS row is the conservative comparison: 40% of Qwen3.6's experts are on
the host and it still decodes 2.55× faster. ~3B active parameters against 27B
dense is the explanation, and it is the reason this architecture is interesting
on a 16 GiB card.

### 8.3 Placement costs decode monotonically, as expected

| IQ4_XS | pp512 | pp8192 | tg128 |
|---|---:|---:|---:|
| `ncpumoe 16` | 366.61 | 402.20 | 40.95 |
| `ncpumoe 20` | 322.51 | 360.29 | 34.37 |
| change | −12.0% | −10.4% | **−16.1%** |

Four more layers on the host cost 14% of decode and 9% of prefill. Decode is
hurt more, which is the expected shape: decode reads every routed expert of
every layer once per token, so host-resident layers add PCIe and CPU time to the
critical path, while prefill amortises that over a batch.

This is what makes the §7 reserve a real trade rather than free safety. For
IQ4_XS the narrowest admissible split at 32k is 16, and 20 is needed at 262144
(§9) — so the Huge window costs about 14% of decode on top of the context.

### 8.4 At equal placement, the quantizations converge

Comparing at the *same* number of host layers, rather than at each one's own
best placement:

| At `ncpumoe 16` | file size | pp512 | pp8192 | tg128 |
|---|---:|---:|---:|---:|
| Q2_K_XL | 11.45 GiB | 384.14 | 472.90 | 44.42 |
| Q3_K_S | 14.30 GiB | **384.83** | 397.86 | 42.53 |
| IQ4_XS | 16.51 GiB | 366.61 | 402.20 | 40.95 |
| spread | **5.06 GiB** | 5% | 19% | **8%** |

Q2_K_XL and Q3_K_S differ by 2.85 GiB and prefill at 384.14 against 384.83 — the
same number. Across the full 5.06 GiB range the decode spread is 10%.

Once a given number of layers is on the host, host-side expert traffic dominates
the critical path and the size of the GPU-resident remainder stops mattering
much. The `ncpumoe 20` pair agrees: Q2_K_XL 332.28 against IQ4_XS 322.51 at
pp512, 3% apart.

**Q2_K_XL's advantage is not that its weights are small — it is that they are
small enough to need no offload at all.** 103.21 t/s at `ncpumoe 0` against
44.42 at `ncpumoe 16` is the same weights, and the whole difference is placement.

This yields an operator rule that the quality suite can only strengthen, never
reverse: **if a profile has to offload N layers anyway, spend the freed budget on
better weights, not on smaller ones.** At `ncpumoe 16` the choice between
Q2_K_XL and IQ4_XS costs about 10% of throughput, and §3 puts two full
quantization steps between them on expert precision. A Huge profile built on Q2
purely because Q2 is small would be paying for size it no longer needs.

### 8.5 Decode cost per host layer, and what it points at

Per-token latency is close to linear in the number of host layers, with a slope
that tracks the quantization's expert size:

| Quantization | expert MiB/layer | measured ms/token by `ncpumoe` | slope ms/layer |
|---|---:|---|---:|
| Q2_K_XL | 251 | 9.69 (0), 15.04 (6), 22.52 (16), 25.22 (20) | 0.77 |
| Q3_K_S | 308 | 17.22 (8), 20.53 (12), 23.51 (16) | 0.79 |
| IQ4_XS | 362 | 24.42 (16), 29.10 (20) | 1.17 |

Local slopes fall slightly as layers accumulate — Q2_K_XL runs 0.89, 0.75, 0.68
across its three intervals — so the fits are mildly concave rather than
straight. Q3_K_S extrapolates back to 10.93 ms at `ncpumoe 0`, against Q2_K_XL's
**measured** 9.69 ms; the larger model being slower when fully resident is the
expected ordering and is a check that the model behaves.

**IQ4_XS is deliberately not extrapolated to `ncpumoe 0`.** Two points in the
concave tail give a slope of 1.03 ms/layer, which projects a GPU-resident
baseline *faster* than Q2_K_XL's measured figure. That is an artefact of
extrapolating a curved function from its steepest segment, and the configuration
is not admissible anyway (§7).

**The slope suggests CPU compute, not memory bandwidth, is the constraint.** Only
8 of 256 experts fire per token, so a host layer reads
`expert_MiB_per_layer / 32` — 7.8 MiB for Q2_K_XL, 11.3 MiB for IQ4_XS. Against
the measured slopes that is roughly **13.5 GB/s** of effective throughput, far
below what dual-channel DDR5 delivers on this part.

If that reading is right, thread count is a live lever, and every cell in this
campaign ran at `-t 8`. `docs/BENCHMARKS.md` already requires a `--threads`
{8, 16} sweep whenever part of the model is CPU-resident. It is **NOT TESTED**
here and is queued as stage 3b of `run-short-medium.ps1`.

### 8.6 The reserve is the performance optimum, not a safety tax

Three contrast cells were measured on placements §7 and §9 rejected. Each
keeps **more** experts on the GPU than the admissible placement beside it, so
each should be faster. None is.

| Weights | placement | pp512 | pp8192 | pp32768 | tg128 | peak shared MiB |
|---|---|---:|---:|---:|---:|---:|
| Q3_K_S | `ncpumoe 6` **rejected** | 409.47 | 423.82 | 373.25 | 51.00 | 1108 |
| Q3_K_S | `ncpumoe 8` admissible | **672.59** | **713.38** | **636.73** | **58.08** | 469 |
| Q3_K_XL | `ncpumoe 8` **rejected** | 339.39 | 333.73 | 315.38 | 42.48 | 1674 |
| Q3_K_XL | `ncpumoe 12` admissible | **454.14** | **473.18** | **456.83** | **48.38** | 482 |
| IQ4_XS | `ncpumoe 12` **rejected** | 271.77 | 275.58 | 256.58 | 40.91 | 880 |
| IQ4_XS | `ncpumoe 16` admissible | **366.61** | **402.20** | **384.85** | **40.95** | 512 |

The IQ4_XS admissible row uses the re-measured run throughout; see §8.

Gain from moving **more** work to the host, admissible over rejected:

| Weights | rejected → admissible | prefill (pp8192) | decode (tg128) |
|---|---|---:|---:|
| Q3_K_S | `n6` → `n8` | **+68%** | +14% |
| Q3_K_XL | `n8` → `n12` | **+42%** | +14% |
| IQ4_XS | `n12` → `n16` | **+46%** | **+0%** |

**Every one of the three prefills faster with two to four more layers on the
CPU**, by 42% to 68%.
That is not what "keep as much as possible on the GPU" predicts, and it is the
result the contrast cells existed to test rather than assume.

The mechanism is the occupancy threshold, and the shared column shows it: the
rejected cells sit at 98–99% occupancy holding 727–1675 MiB of shared memory,
while the admissible ones sit at 87–93% with shared at the desktop's own 423 MiB
floor. Once the adapter is paging, the experts that remain on it are being
fetched over PCIe anyway — so keeping them there buys nothing and costs the
prefill path badly.

Prefill absorbs almost all of the penalty — the admissible placement prefills
42% to 68% faster — while decode gains a more modest 14%, and for IQ4_XS the
decode comparison is still pending.
That matches the Qwen3.8 campaign's finding that the cliff decides prefill, and
it matters for an agentic profile: prefill is what a large standing context
costs on every turn.

**So the answer to "is full GPU residency optimal" is neither yes nor no.** It is
optimal exactly when it is admissible — Q2_K_XL at `ncpumoe 0` measures 2324 t/s
at pp512, the fastest cell in the campaign — and actively harmful when it pushes
past the threshold. The criterion is not how much fits on the card; it is how
much fits below the cliff.

The spread instrument agrees independently. Q3_K_XL at `ncpumoe 8` returned
tg128 at **9.11% relative standard deviation**, the only healthy-process cell in
the campaign above the 8% warning line, against 4.13% for the admissible
placement beside it. Oscillation across the paging boundary is visible in the
variance as well as in the mean.

### 8.7 `--load-mode none` is the largest single lever measured

The runtime asks for this itself. Loading with `--n-cpu-moe` emits
`tensor overrides to CPU are used with mmap enabled - consider using
--load-mode none for better performance`. Q3_K_XL at `ncpumoe 12`, both arms
back to back under identical conditions:

| | `auto` (mmap) | `none` | change |
|---|---:|---:|---:|
| pp512 | 267.95 ± 6.39 | **1283.63 ± 13.04** | **+379%** |
| pp8192 | 319.41 ± 23.42 | **483.27 ± 4.74** | **+51%** |
| tg128 | 41.53 ± 1.89 | **53.30 ± 0.70** | **+28%** |

And what it costs, from a `llama-server` load of the same configuration:

| | `auto` | `none` |
|---|---:|---:|
| commit | 12.00 GiB | **16.48 GiB** |
| shared GPU | 794 MiB | **5411 MiB** |
| process working set | 11.91 GiB | 4.81 GiB |
| load time | 6.5 s | 10.6 s |

**The mechanism is where the host-resident experts live.** Under `auto` they are
mmap'd, pageable `CPU_Mapped` memory; §7.4 measured that this costs no commit,
which looked like a free lunch. It is not free under memory pressure — the OS
evicts those pages and each pass re-reads them. Under `none` they are pinned
host memory the GPU can reach directly, which is the 5411 MiB of "shared" and
the 4.5 GiB of extra commit. The working set falls because the pages are no
longer charged to the process as mapped file pages.

Two consequences beyond the speed-up.

**The shared-memory rule in §9.2 does not apply to this mode.** That rule reads
shared memory above the idle baseline as paging, and it was calibrated entirely
on mmap-based offload. Under `--load-mode none`, 5.4 GiB of shared memory is the
placement working as designed. The criterion is specific to the mechanism and
cannot be applied blind.

**This is the evidence that justifies proposing `load_mode` as a manifest
field.** §8 of the campaign plan deferred it explicitly until measured, on the
grounds that the repository should not carry a knob that only ever holds its
default. A 379% prefill difference is not that.

**Not yet confirmed:** the `auto` arm here measured 267.95 t/s at pp512 against
454.14 in Phase 2 for the same configuration, because the desktop was heavier by
then (§8.9). The A/B is internally valid — both arms ran minutes apart under the
same conditions — but the absolute figures are depressed and the ratio needs
re-confirming at a controlled baseline. The direction is not in doubt.

### 8.8 Sixteen threads nearly doubles prefill, and does nothing for decode

`docs/BENCHMARKS.md` requires this sweep whenever part of the model is
CPU-resident, and every other cell in this campaign ran at `-t 8`. Q3_K_XL at
`ncpumoe 12`:

| | `-t 8` | `-t 16` | change |
|---|---:|---:|---:|
| pp512 | 427.32 ± 10.1% | 480.03 ± 3.3% | +12% |
| pp8192 | 283.44 | **503.94** | **+78%** |
| tg128 | 48.60 | 48.11 | −1% |

The repository's own expectation is the opposite — `docs/BENCHMARKS.md` records
that "on an 8C/16T part SMT contention often makes 8 the faster choice". That
holds for a dense model with a few CPU-resident layers. It does not hold here,
and the split between the two axes says why: prefill on host experts is a large
batched GEMM that parallelizes across SMT threads, while decode processes one
token at a time and is latency-bound, so the extra threads have nothing to do.

Prefill is what an agentic profile pays on every turn with a large standing
context, so a 78% gain on that axis at no decode cost is worth taking.

**Both levers act on prefill, and neither is in the campaign's defaults.** Every
throughput figure in §8.1 to §8.6 was measured at `-t 8` and `-lm auto`. They
remain valid as a comparison between placements, because the setting was held
constant; they understate what a tuned profile would deliver.

### 8.9 The desktop's VRAM is a campaign variable, and it moved

ADR 0011 records that the budget available to a model "moves with whatever is on
screen" and puts the desktop at roughly 3.0 GiB. Over this campaign it was
measured between **2474 MiB and 4350 MiB**, and it moved *during* the campaign:

| When | Idle dedicated | Idle shared | Commit |
|---|---:|---:|---:|
| Phase 1, 14:41 | 2474–2700 MiB | 322 MiB | 22.1 GiB |
| Refinement, 17:44 | 3535–3740 MiB | 394 MiB | 26.2 GiB |

By process, at the busier end: AMD Radeon Software 1858 MiB, Firefox 997 MiB,
dwm 671 MiB, Discord 254 MiB, explorer 163 MiB, and several smaller clients —
about 4350 MiB with the machine in ordinary use.

**A 1.2–1.9 GiB swing is larger than the entire 1 GiB admission reserve.** Every
placement selected against the quiet baseline loses that much headroom when the
operator opens a browser. This is not a defect in the measurements; it is the
operating condition, and it is why this campaign ships two profile sets rather
than one — see §12.

It also bounds what a marginal figure can carry. §7.5 established that marginal
VRAM reproduces to 0.16% between runs, which is true **for a configuration that
is not spilling**. Once a cell crosses into shared memory its marginal dedicated
figure falls, because the driver is satisfying part of the request elsewhere:
Q2_K_XL at 262144 measures 11878 MiB marginal at `ncpumoe 8` on a quiet desktop
and 10695 MiB at `ncpumoe 7` on a busy one, which reads as the wider split
costing more VRAM. It does not. The `ncpumoe 7` cell is spilling 1667 MiB.
**Marginal VRAM is only comparable across baselines for cells that pass the
shared-memory test**, and an earlier revision of this report's gap analysis
omitted that filter and drew a wrong conclusion from it.

### 9.1 What fits at each window

**This section previously reported that `q8_0` cache is a 32k-only option. That
was wrong, and the manner of the error is this campaign's most repeated one.**
Phase 3 probed `q8_0` at 131072 in four cells, each at a placement the 32k sweep
had already shown sufficient, and all four were rejected. "Rejected at the four
placements I tried" was then written up as "does not fit" — and 262144 / `q8_0`
was skipped entirely on the reasoning that it cannot fit if 128k does not, which
inherited the same unexamined premise. A later search that lets `--n-cpu-moe`
run out to 28 finds **every `q8_0` window admissible on every quantization, 24 of
24 rows**. The cache was never the obstacle; the placement window was.

The corrected figures come from `Invoke-Qwen36BudgetSearch.ps1`, which differs
from Phase 3 in two ways that make the two tables non-comparable, so the Phase 3
numbers are not restated here. It selects on **marginal** VRAM plus a stated
desktop allowance rather than on the raw headroom a cell happened to record
(§8.9 — raw headroom carries whatever desktop was present at measurement time),
and it discards any cell that spills more than 400 MiB into shared **before**
reading its marginal figure (§7.1 — a spilling cell's marginal *falls* as the
configuration gets worse, so reading it after the fact inverts the ranking).

arithmetic in §2.1 can be trusted for planning.

### 9.2 A paging case the ADR 0011 classifier does not catch

`Q3_K_S` at 131072 / `q8_0` / `ncpumoe 8` is reported **`ok`** and is **not**
admissible. It holds 1515 MiB of shared memory above the idle baseline at 93.6%
occupancy. ADR 0011's rule reaches `pressured` only when occupancy ≥ 95% **and**
shared ≥ 1024 MiB, and `elevated` on occupancy alone — shared never raises a
verdict by itself. On Qwen3.8 the two moved together, so the rule held. Heavy MoE
offload breaks that coupling: it lowers occupancy while the remainder still
spills.

Marginal shared memory separates all 60 cells in this campaign with no overlap:

| | shared above idle |
|---|---|
| Healthy cells | 101–227 MiB, rising slightly with context |
| Paging cells | 512–3720 MiB |

The campaign's selection scripts therefore reject a cell whose shared margin
exceeds 400 MiB, a threshold sitting in an empty band between the two clusters.

**This is deliberately not proposed as a change to `internal/edge/gpumemory.go`.**
The edge samples a live adapter with the model already loaded and has no idle
baseline to subtract, so it cannot compute this quantity at all. Recalibrating
the edge's own thresholds is a separate question needing separate evidence, and
the classifier gates nothing — admission control uses `resources.peak_vram_gib`
against the declared device budget, not this verdict. Recorded here as a
measured limitation rather than acted on.

### 9.3 The spill/no-spill boundary is bistable, not noisy

The 400 MiB threshold in §9.2 separates the clusters cleanly, but eight cells in
the placement tables spill at `n` while a *lower* `n` — fewer experts on the
host, so strictly more device memory demanded — reads clean. Placement cannot
explain that ordering, and all eight are `q4_0`; no `q8_0` cell does it.

Two explanations fit, and they point opposite ways. If the spill is transient
desktop state (§8.9), the search skipped placements that were in fact admissible
and every profile is wider and slower than it needs to be. If it is structural,
the skip was right. `Test-Qwen36SpillReproduction.ps1` separates them by
re-measuring all eight and keeping both readings rather than overwriting: seven
reproduced, one did not.

But the magnitudes say something neither explanation predicted — **every one of
the eight read lower on the repeat**:

| Cell | 1st | 2nd | |
|---|---:|---:|---|
| Q2_K_XL 131072 `n2` | 875 | 635 | reproduced |
| Q2_K_XL 262144 `n6` | 1667 | 995 | reproduced |
| Q3_K_S 131072 `n10` | 1327 | 592 | reproduced |
| Q3_K_S 262144 `n14` | 1667 | 1007 | reproduced |
| Q3_K_XL 131072 `n14` | 875 | 633 | reproduced |
| Q3_K_XL 262144 `n18` | 1033 | 235 | did not |
| IQ4_XS 32768 `n14` | 401 | 410 | reproduced |
| IQ4_XS 262144 `n18` | 1666 | 1033 | reproduced |

So it is not one or the other: a structural floor with a desktop-dependent
component on top. The dichotomy the test was built around was a false one.

The mechanism showed up in two runs of Q3_K_XL / 262144 / `n18` nineteen seconds
apart — one cold (14.6 s load), one warm (6.5 s) — which returned **identical
figures to 0.1 MiB**: dedicated 15633.3, shared 615.3, idle dedicated 3582.6,
idle shared 388.2. Nothing on the desktop moved between them and the allocator
returned exactly the same answer.

That makes the behaviour **deterministic given the starting state, not random.**
Near the fit boundary WDDM has two available outcomes — pack dedicated VRAM to
the ceiling, or satisfy part of the allocation from shared — and which one it
takes is decided by what is already resident. This is what allows "clean at `n`,
spilling at `n+2`, clean at `n+4`" without any non-monotonic memory demand: the
three cells are not three points on one curve, they are two branches.

Two cells decided profiles, so both were read four times:

- **Q3_K_XL / 262144 / `q4_0`.** `n18` read 1033, 235, 227, 227 MiB. The first
  was the outlier. `n17`, which the step-of-2 sweep never measured, spills
  reproducibly (1667, 1008, 1050), and `n16` is clean but over the budget cap at
  12731 MiB. So `n18` is the first admissible placement at single-layer
  resolution, and the `dedicated` profile moves from `n20` to **`n18`** — two
  expert layers returned to the device, which §8.3 prices in decode.
- **IQ4_XS / 32768 / `q4_0`.** `n14` was rejected on a 401 MiB spill against a
  400 MiB margin, which is close enough to be worth checking. It read 410, 417
  and 102 MiB on three further runs: three of four above the margin. **The
  rejection stands**, and `n16` ships. A cell that lands on the margin in most
  runs is what the margin is for.

Operationally this is an argument for the margin over the bare reserve, already
made on throughput grounds in §8.6 and §7.5: a configuration selected at the
boundary is not merely close to failing, it is one desktop state away from a
different allocation. Readings for all eight cells and both decision cells are in
`summary-spill-reproduction.json` and `summary-spill-bistability.json`.

## 10. Reasoning behaviour — partial

**MEASURED so far**, from the Phase 0 gate:

- `reasoning_content` is a separate field on the response; it is not mixed into
  `content`, and no `<think>` marker leaked into the answer.
- A trivial prompt ("Reply with exactly: READY") produced 504 characters of
  reasoning and 131 completion tokens, and terminated with `finish_reason:
  stop` and the correct answer. Reasoning is not free even on a trivial turn,
  but it terminates.
- The generation prompt opens `<think>` unconditionally; the template also
  accepts `enable_thinking: false`, which injects an empty think block.

**Template contract, read from the Jinja source** (`chat-template-ud-q3ks.jinja`,
SHA-256 of the copy the server loaded: `55D49314…39F9EA0C`):

- Historical reasoning is re-rendered only for assistant messages *after the last
  user query* — i.e. within the current turn's tool-call chain — unless
  `preserve_thinking` is set.
- The runtime detected this and logs `chat template supports preserving
  reasoning, consider enabling it via --reasoning-preserve`. That flag exists on
  b10549 and is **not** used by this campaign.

**The server is stateless and this does not change that.** Nothing on the server
remembers the previous turn's reasoning. In-turn preservation works only if the
harness sends `reasoning_content` back on assistant messages it replays. That is
a harness responsibility and is recorded here as one; the campaign does not add
server-side history to make it work.

**NOT TESTED yet:** whether reasoning terminates usefully under a hard prompt
with a bounded output — the failure ADR 0012 added `reasoning_budget` for, where
a model spends its whole allowance thinking and returns an empty answer. Phase 4
records `reasoning_chars` and `no_answer` per task, and `edge_contract.py`'s
`reasoning_separation` and `reasoning_roundtrip` probes cover the rest. **No
`n_predict` or `reasoning_budget` value is proposed until that evidence exists**;
Phase 4 runs at the same defaults the Qwen3.8 profiles were graded under so the
comparison is a comparison.

### 12.1 Two sets, because the desktop is not a constant

§8.9 measured the desktop holding between 2474 and 4350 MiB of VRAM during this
campaign, a swing larger than the whole admission reserve. A single set of
profiles would have to be either too slow for a machine that is only serving the
model, or unsafe on one that is also running a browser.

The operator's decision, recorded here as the campaign's: **ship two sets.**

| Set | Desktop allowance | Budget for the model | For |
|---|---:|---:|---|
| `workstation` | 4400 MiB | marginal ≤ 10880 MiB | The machine is in ordinary use — browser, chat clients, Radeon Software |
| `dedicated` | 2700 MiB | marginal ≤ 12580 MiB | The machine is serving the model and little else |

Both budgets are measured, not chosen: 4400 MiB is the per-process sum with the
usual applications open, and 2700 MiB is the highest idle observed across the
quiet Phase 1 sweep. Both then subtract the same 1 GiB reserve from
`docs/MODEL_PROMOTION.md`.

Selection uses **marginal** VRAM plus the allowance rather than the raw headroom
a cell happened to record, because the raw figure carries whatever desktop was
present when that cell ran. Per §8.9 that substitution is only valid for cells
that pass the shared-memory test, so a spilling cell is excluded before its
marginal figure is used, not after.

Both sets are now measured. `workstation` initially was not — the wider
placements it needs at 131072 and 262144 had never been run, because the coarse
sweep stopped where the quiet-desktop budget stopped. Extending `--n-cpu-moe`
out to 28 resolved every row in both sets and, in passing, overturned this
report's `q8_0` finding (§9.1). That is the same error twice from one cause:
**a sweep sized against one budget was read as a statement about the hardware.**

What the completed phases have already constrained:

- **The taxonomy may not need three quantizations.** On Qwen3.8 each profile
  class required different weights because the weights were what did not fit.
  Here §9 shows `UD-IQ4_XS` — the best candidate — holding 32768, 131072 and
  262144. If quality confirms it, the classes differentiate by context, cache
  precision and placement rather than by quantization.
- **There is a real speed/quality frontier to resolve.** §8 measures Q2_K_XL
  fully resident at 103.21 t/s decode against IQ4_XS at 40.95 t/s. A 2.5× decode
  difference is large enough that the coding suite has to decide it, not a
  preference for better weights.
- **`q8_0` cache is available at every window** (§9.1), at a cost of 0 to 6
  extra host layers over `q4_0`. It is therefore a profile axis rather than a
  32k-only luxury — but nothing here measures whether the extra cache precision
  buys anything, since no quality run in this campaign varied cache type. Absent
  that evidence, `q4_0` remains the default and `q8_0` stays unproposed.

Whether one, two or three profiles are justified is deliberately left open. A
class will be proposed only where a measurement supports it.

## 15. Unresolved risks

1. **Decode against a filled window is unmeasured.** §9 measures what *fits* at
   131072 and 262144; `llama-bench` has no `--ctx-size` and derives its context
   from `-p + -n + -d`, so every throughput figure in §8 is short-context. A
   256k profile cannot ship on fit alone. Queued for the overnight block.
2. **`tool_choice` object form is silently ignored by this runtime** (§6.3,
   independently reproduced in §11.2). It affects every model on b10549, and
   there is nothing in the response for a harness to detect it by. Recommended
   follow-up: have the edge refuse the object form with `400
   unsupported_feature`, matching the rule `docs/BENCHMARKS.md` already sets.
   **Not changed in this campaign** — it alters behaviour for existing models
   and deserves its own change with its own tests.
3. **ADR 0011's pressure classifier misses a paging case on this architecture**
   (§9.2). Observability only; it gates nothing. Any tooling that trusts it on a
   heavily-offloaded MoE will admit a configuration that pages.
4. **The desktop's VRAM hold moves the budget.** §8.9 measured it between 2474
   and 4350 MiB during this campaign — a swing larger than the whole 1 GiB
   reserve. §7.5 shows marginal figures reproduce to 0.16% regardless, but the
   absolute headroom an operator has is not a constant. This is why two profile
   sets ship rather than one.
5. **Near the fit boundary the allocator is bistable** (§9.3), and the branch it
   takes is set by resident desktop state. A configuration selected at the bare
   reserve is not merely close to failing; it is one desktop state away from a
   different allocation. Both shipping sets add a margin over the reserve.
6. **Cache precision is unqualified.** §9.1 shows `q8_0` fits at every window,
   §11.1 graded only `q4_0`. Whether the extra precision changes output is not
   measured, so `q8_0` is not proposed.
7. **Context beyond 262144 is not exposed and not tested**, despite upstream
   advertising an extension.
8. **Two of three contract legs have not run** (§11.2). Only the direct port is
   measured; llama-swap and the edge are not. `capabilities.function_calling`
   stays false until the edge leg passes.
9. **`--device ROCm0` selects the iGPU unless the environment says otherwise.**
   This host enumerates gfx1036 first and gfx1201 second, and without
   `HIP_VISIBLE_DEVICES=1` the server loads, serves `/v1/models` with 200, then
   aborts on the first completion with a rocBLAS `TensileLibrary.dat` error for
   gfx1036. The first run of §11.2 hit exactly this and recorded 0/9 — a
   connection failure read as a model failure. Eight scripts set the variable
   inline; `Enter-V2RocmEnvironment` in `scripts/v2/Common.ps1` now provides it
   next to the argument builder that emits `--device`. **The existing eight are
   deliberately not rewritten** — they work, and changing them mid-campaign
   risks a regression for no measurement gain.
10. **Manifest entries do not exist yet.** Nothing has been added to
    `config/models.yaml`, and no client catalog has been regenerated.

## Appendix H - Repeat readings of the two decision cells

Near the fit boundary the WDDM allocator takes one of two branches - pack dedicated VRAM to the ceiling, or satisfy part of the allocation from shared - and which branch it takes is decided by what is already resident, not by chance. Two runs of q3kxl/262144/n18 nineteen seconds apart, one cold (14.6 s) and one warm (6.5 s), returned byte-identical dedicated, shared and idle figures. The branch is therefore reproducible for a given desktop state and varies only when the desktop varies. This is what makes 'clean at n, spilling at n+2, clean at n+4' possible without any non-monotonic memory demand: the three cells are not three points on one curve, they are two different branches.
