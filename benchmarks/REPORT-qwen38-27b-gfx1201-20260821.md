### Runtime packaging note

The official `llama-b10549-bin-win-rocm-7.14-x64.zip` ships `ggml-hip.dll` but **no
rocBLAS closure**. It fails to load with Win32 error 126 until these are supplied:

```
hipblas.dll  rocblas.dll  rocsolver.dll  libhipblaslt.dll  amd_comgr0702.dll  rocblas\  hipblaslt\
```

They were copied from the pinned `llama_cpp_b8407_rocm_7.2.1` package (117.7 MB
`rocblas\` Tensile tree). `amdhip64_7.dll` must **not** be copied — it has to match
the installed driver and is resolved from `System32`. `C:\Windows\System32\downlevel`
must be on `PATH` for the UCRT API sets, which `scripts/bench-llama.ps1` already does.

This is a **ROCm 7.2.1 rocBLAS against a ROCm 7.14 ggml-hip build**. It is
validated only by the correctness pass in §2; treat it as a stopgap, not a
qualified runtime.

### Device selection trap

`b10549` enumerates **two** ROCm devices, unlike the pinned `b8407`:

```
ROCm0: AMD Radeon(TM) Graphics  gfx1036   (iGPU, 12459 MiB)
ROCm1: AMD Radeon RX 9070 XT    gfx1201   (16304 MiB)
```

`bench-llama.ps1` hardcodes `--device ROCm0`, so its `amd` branch would benchmark the
**iGPU** on this runtime. All runs below use `-Runtime unsloth`, whose branch sets
`HIP_VISIBLE_DEVICES=1` and makes the dGPU `ROCm0`.

## 1. `blk.64` MTP-head gate

`model-test-matrix.json` requires the MTP head at Q5_K or better; at Q4_K draft
acceptance measures 0% and speculation fails silently. Verified by reading only the
GGUF header over HTTP range requests (16.8 MB per file, no full download):

| GGUF | `blk.64` weight quants | Verdict |
|---|---|---|
| `bartowski/Qwen3.8-27B-GGUF` → `Qwen3.8-27B-IQ4_XS.gguf` | **Q4_0** | **FAIL** |
| `unsloth/Qwen3.8-27B-GGUF` → `Qwen3.8-27B-UD-IQ4_XS.gguf` | Q6_K / Q8_0 | PASS |
| `unsloth/Qwen3.8-27B-GGUF` → `Qwen3.8-27B-UD-Q4_K_M.gguf` | Q6_K / Q8_0 | PASS |

All three carry the 4 `blk.64.nextn.*` tensors, so the head is present in each; only
its precision differs. This resolves the `repo: TBD` field on every `qwen38-*`
profile in the matrix to **`unsloth/Qwen3.8-27B-GGUF`**. Note the filename differs
from the matrix's `Qwen3.8-27B-IQ4_XS.gguf` — the passing artifact is the `UD-`
prefixed one.

## 2. Gate zero — is the Gated DeltaNet kernel accelerated on gfx1201?

`docs/BENCHMARKS.md` records `GGML_OP_GATED_DELTA_NET` as CPU+CUDA only, with the HIP
path measuring at CPU speed on gfx1151, and marks gfx1201 `unverified`.

**Op support** (`test-backend-ops support`): 36/36 `GATED_DELTA_NET` cases
`SUPPORTED` on ROCm1, 0 unsupported. No CPU fallback.

**Correctness** (`test-backend-ops test -b ROCm1`): 36/36 pass against the CPU
reference. This also validates the mixed rocBLAS packaging for this op.

**Kernel throughput** (`test-backend-ops perf`), at Qwen3.8-27B's shape
`head_count=32, head_size=128`:

| `n_seq_tokens` | ROCm1 gfx1201 | CPU | Speedup |
|---:|---|---|---:|
| 1 (decode) | 4.72 µs — 840.75 GB/s | 25.14 µs — 157.84 GB/s | 5.3x |
| 1 (`kda=1`) | 4.76 µs — 836.30 GB/s | 30.10 µs — 132.32 GB/s | 6.3x |
| 64 | 77.04 µs — 101.62 GB/s | 813.32 µs — 9.63 GB/s | 10.6x |
| 256 | 298.61 µs — 65.64 GB/s | 3308.60 µs — 5.93 GB/s | 11.1x |
| 512 | 596.24 µs — 59.23 GB/s | 6831.68 µs — 5.18 GB/s | 11.5x |
| 1024 | 1210.85 µs — 55.15 GB/s | 13442.50 µs — 5.00 GB/s | 11.1x |

**Verdict: PASS.** gfx1201 does not inherit the gfx1151 CPU-speed HIP path. The
per-token collapse from 840 GB/s to ~55 GB/s as the scan lengthens is inherent to the
recurrence, not a backend defect — the GPU keeps an 11x margin over CPU throughout.

The model-level control agrees: same weights at `-ngl 0` (host-resident) decode at
**2.70 t/s** against **18.80 t/s** resident, a 7.0x gap.

## 3. Weight split — the load-bearing result

All rows: `UD-IQ4_XS`, `-ngl 99`, `-fa 1`, `-ub 512`, `-ctk/-ctv q8_0`, `-t 8`,
3 repetitions, `--split-mode none`, device isolated to gfx1201. The `-ot` column is
the count of trailing blocks whose `ffn_.*` tensors were pinned to CPU.

| FFN blocks on CPU | `-ot` pattern | pp512 | pp8192 | tg128 |
|---:|---|---:|---:|---:|
| 0 | *(none)* | 269.81 ± 1.30 | 254.70 ± 0.36 | 18.80 ± 0.08 |
| 4 | `blk\.(6[0-3])\.ffn_.*` | 302.69 ± 1.69 | 251.14 ± 0.12 | **23.25 ± 0.11** |
| 6 | `blk\.(5[8-9]\|6[0-3])\.ffn_.*` | 688.24 ± 6.43 | — | 17.40 ± 0.24 |
| 8 | `blk\.(5[6-9]\|6[0-3])\.ffn_.*` | **1034.91 ± 12.89** | **921.04 ± 2.81** | 17.42 ± 0.37 |
| 12 | `blk\.(5[2-9]\|6[0-3])\.ffn_.*` | 939.51 ± 40.72 | — | 14.63 ± 0.01 |
| 20 | `blk\.(4[4-9]\|5[0-9]\|6[0-3])\.ffn_.*` | 836.58 ± 10.23 | — | 11.09 ± 0.11 |

**At short prompt lengths full GPU residency is the worst configuration on both
axes.** It is beaten on decode by a 4-block split (+24%) and on prefill by an
8-block split (+284% at 512, +262% at 8192). That inverts both the conventional
"fit it all in VRAM" rule and the **modelled** table in `docs/TUNING.md` §1, which
predicts monotonic degradation from full residency onward.

### 3.1 The split advantage is a short-prompt effect and it collapses

Prefill across prompt length, same settings:

| Prompt tokens | Full GPU | 4-block split | 8-block split |
|---:|---:|---:|---:|
| 512 | 269.81 ± 1.30 | 302.69 ± 1.69 | **1034.91 ± 12.89** |
| 8192 | 254.70 ± 0.36 | 251.14 ± 0.12 | **921.04 ± 2.81** |
| 16384 | 244.24 ± 0.34 | **264.67 ± 0.34** | 247.34 ± 0.98 |
| 32768 | 221.09 ± 0.38 | **234.18 ± 0.94** | 195.03 ± 0.82 |

The 8-block split holds a 3.6-3.8x lead through 8192 tokens, then falls off a cliff:
921.04 → 247.34 between 8k and 16k, a 73% loss, and by 32k it is the **slowest** of
the three. Full residency loses only 13% across the same 512→32768 range, and the
4-block split loses 23%.

By 16384 tokens all three configurations converge into a 244-265 band and weight
placement stops being the dominant variable. That band is consistent with the Gated
DeltaNet scan taking over as the bottleneck: §2 measures the GDN kernel falling from
840 GB/s at one token to ~55 GB/s at 1024, and unlike the FFN matmuls that cost is
identical in every configuration. **Below ~16k the binding constraint is VRAM
overcommit; above it, the recurrence.**

The overcommit mechanism reaches the split too. Sampled during the 32k split run the
adapter held 15916 MiB dedicated with **1253 MiB shared**, against 514 MiB shared for
the same split at 512 tokens. Once a configuration is spilling anyway, its
CPU-resident FFN blocks are pure added cost.

`UD-Q4_K_M` (15.32 GiB, cannot fit) at the 20-block split: pp512 **831.35 ± 12.63**,
pp8192 **765.30 ± 6.24**, tg128 **10.37 ± 0.05** — statistically identical prefill to
`IQ4_XS` at the same split (836.58), which rules the **quant** out as the cause and
isolates the effect to the **split**.

### Root cause: the adapter is shared, and the load log cannot see that

llama.cpp's own accounting shows no shortage at `n_ctx=512` — model 12726.35 MiB,
compute 505.78 MiB, KV 17.00 MiB, recurrent state 149.62 MiB, ~13.4 GiB of 15.9 GiB.
Windows GPU performance counters, sampled during the runs, disagree:

| Config | Peak dedicated VRAM | Peak shared (system) | pp512 |
|---|---:|---:|---:|
| Full GPU | **16071 MiB / 16304 (98.6%)** | **1350 MiB** | 273.14 ± 1.72 |
| 8-block split | 15720 MiB (96.4%) | 514 MiB | 1033.51 ± 6.59 |

**An earlier revision of this report attributed the gap to llama.cpp
under-reporting its own allocations. That was wrong, and the correction matters
because it changes the fix.** Sampling idle against peak separates the two
contributions:

| Quantity (4-block split, `ub` 288) | Value |
|---|---:|
| Adapter dedicated, idle, no model loaded | 2967 MiB |
| Adapter dedicated, peak under load | 15928 MiB |
| **Marginal — what the model actually cost** | **12961 MiB** |
| What llama.cpp charged the process | 13012 MiB |

llama.cpp's figure is accurate to within 0.4% of the model's real marginal cost.
What it omits is everything else on the card. This workstation's desktop
compositor and browser hold **roughly 3.0 GiB before any model loads**, so a
12.7 GiB model on a 16.3 GiB adapter sits at 97-98% occupancy rather than the
80% the load log implies. Past that point the AMD driver pages the excess over
PCIe. Prefill sweeps the whole weight set in large batches and is punished
heavily; decode streams weights in a prefetchable order and barely moves
(18.80 → 17.42).

Two consequences follow, and neither is "llama.cpp is lying":

1. **The budget available to a model is not the card's capacity.** On this
   workstation it is roughly 16.3 − 3.0 = **13.3 GiB**, and it moves with
   whatever else is on screen. A static manifest cannot know that figure, which
   is why the live adapter probe added in §8 exists.
2. **Size against the driver counters, not the load log** — not because the log
   is inaccurate, but because it answers a narrower question than the one that
   decides whether the driver starts paging.

### Confounds eliminated

Each tested against the full-GPU configuration, which is pinned at ~270 t/s pp512:

| Variable | Values | pp512 | Effect |
|---|---|---|---|
| `--threads` | 8 / 16 | 269.81 / 271.95 | none |
| `--ubatch-size` | 288 / 512 / 1024 / 2048 | 275.01 / 269.81 / 272.02 / 272.21 | none |
| matmul path | default / `GGML_CUDA_FORCE_CUBLAS=1` / `GGML_CUDA_FORCE_MMQ=1` | 266.63 / 272.63 / 271.46 | none |
| fused ops | — | identical logs | none |

`resolve_fused_ops` reports fused Gated DeltaNet (autoregressive **and** chunked)
enabled in both configurations, so the split does not change the GDN path. Mirror
control at `-t 16` on the 8-block split: pp512 1036.77 ± 10.12 — the split effect is
independent of thread count.

The `--ubatch-size` result is worth recording on its own: the 40x dead band that
`model-test-matrix.json` warns about is **not** observable here at 288 vs 512 vs 1024
vs 2048. The band's lower edge (65..256) was not swept, per the schema's refusal.

## 4. Against the comparison points

`docs/BENCHMARKS.md` requires judging against evidence, not an invented threshold.

**Repo baseline** — Qwen3.5-9B Q4_K_M, 5.28 GiB, same GPU, build b8407, kv q4_0:
pp512 **3775.78**, tg128 **80.78**. Control variables differ (build, KV type), so this
is an order-of-magnitude reference only.

| Axis | Size-scaled expectation from 9B | Best measured 27B | Ratio |
|---|---:|---:|---:|
| tg128 (bandwidth-scaled, 13.26/5.28 = 2.51x) | 32.2 t/s | 23.25 t/s | 0.72 |
| pp512 (param-scaled, 27.32/8.95 = 3.05x) | 1238 t/s | 1034.91 t/s | 0.84 |

**Modelled ceiling** — `docs/TUNING.md` §1, `1/(W/BW)` with `BW_gpu` 640 GB/s:
14.25 GB fully resident gives 44.9 t/s theoretical, **35.9 t/s at 80% utilization**.
Best measured decode is 23.25 t/s, **65% of the modelled 80% figure**. The shortfall is
consistent with the hybrid's 48 recurrent layers, whose per-token state update is
latency-bound rather than bandwidth-bound and is not represented in that formula.

Neither axis is an order of magnitude below its comparison point, so the abort
condition in `docs/BENCHMARKS.md` is not met. **The expensive profiles are worth
running.**

One caveat on that verdict: the reassuring `pp8192/pp512` ratio of 89% belongs to the
8-block split, and §3.1 shows it does not survive to 16k. Judged at 32768 tokens the
best prefill figure is 234.18 t/s — 19% of the size-scaled 9B expectation rather than
84%. Long-context prefill on this hybrid is roughly 4x worse than a dense model of
equivalent size would suggest, and that is the number an agentic profile should be
planned against.

## 5. Recommended configuration

**Default — 4-block split.** It is the only configuration that beats full residency
on every axis measured, and the margin is largest exactly where an agentic workload
lives: decode, and prefill at long context.

```
-ot "blk\.(6[0-3])\.ffn_.*=CPU"  -ngl 99 -ub 512 -fa 1 -ctk q8_0 -ctv q8_0 -t 8
```

| vs full residency | pp512 | pp8192 | pp16384 | pp32768 | tg128 |
|---|---:|---:|---:|---:|---:|
| 4-block split | 302.69 | 251.14 | 264.67 | 234.18 | 23.25 |
| Full GPU | 269.81 | 254.70 | 244.24 | 221.09 | 18.80 |
| Delta | +12% | −1.4% | +8% | +6% | **+24%** |

The only regression is a 1.4% dip at 8192, inside the range where the 8-block split
is 3.6x faster anyway.

**Use the 8-block split only if prompts are reliably ≤8k**, where it is worth
3.6-3.8x on prefill for a 7% decode cost. It is the wrong default: past 16k it loses
to both alternatives, and an agentic harness with a growing standing context will
cross that line and stay there.

```
-ot "blk\.(5[6-9]|6[0-3])\.ffn_.*=CPU"    # short-prompt profile only
```

**Do not ship full residency.** It is not the safe choice it appears to be — it is
last or near-last on every axis measured, for the reason in §3.
