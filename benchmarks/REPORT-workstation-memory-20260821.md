## 2. Problems found

Five, of which only the last is a tuning question.

**2.1 — A wrong claim in this repository's own report.** The earlier revision of
`REPORT-qwen38-27b-gfx1201-20260821.md` stated that llama.cpp under-reports VRAM
by ~2.7 GiB. Sampling idle against peak disproves it: llama.cpp charged the
process 13012 MiB and the model's marginal adapter cost was 12961 MiB, agreeing
to 0.4%. The missing 3.0 GiB is the **desktop**, which holds it before any model
loads. The correction matters because it changes the fix: the budget available to
a model here is ~13.3 GiB, not 15.9, and it moves with what is on screen. The
report has been corrected in place with the superseded claim called out.

**2.2 — Every memory column in every agentic report on this machine was empty.**
`Get-V2CommitGiB` read `\Memory\Committed Bytes`, a localized counter path that
does not resolve on pt-BR Windows. The helper caught the failure and returned
`$null`, so a measurement that never happened was indistinguishable from one that
was not requested.

**2.3 — `Test-V2AgenticHarness.ps1` could not pass on this machine.** Windows
PowerShell 5.1 wraps a native command's redirected stderr in a terminating error
record; the harness deliberately runs a scenario that writes to stderr. CI runs
`pwsh` 7, where it passes. The gate was green while being unrunnable locally.

**2.4 — `resources.peak_commit_gib` was fed the wrong quantity.** The edge
compares `peak_commit_gib + 4 GiB` against *available* commit headroom, so the
field must be the model's own demand. The script recorded system-wide committed
bytes — an absolute level. On this workstation that is ~40 GiB against ~36 GiB of
headroom, so a correctly-measured manifest would have been refused by its own
gate.

**2.5 — The VRAM reserve was too small by a factor of three.** `vramReserveGiB`
was an estimated 1.0 GiB. Measured idle, the desktop holds 2938–3126 MiB. A
12.45 GiB model on a 15.92 GiB card was being admitted as if it would reach 84%
occupancy; it actually reaches 97%.

## 3. Changes implemented

**Profiles.** Five candidates in the canary deployment, all on
`amd-rocm-qwen38`, all `parallel: 1`, `context_shift: false`, `threads: 8`,
`gpu_layers: 99`, `ubatch_size: 288`:

| id | ctx | KV | `-ot` split |
|---|---:|---|---|
| `qwen38-27b-ws-32k` **(default)** | 32768 | `q8_0` | 4 blocks |
| `qwen38-27b-ws-64k` | 65536 | `q8_0` | 4 blocks |
| `qwen38-27b-ws-128k` | 131072 | `q8_0` | 4 blocks |
| `qwen38-27b-ws-8k-prefill` | 8192 | `q8_0` | 8 blocks |
| `qwen38-27b-ws-32k-kv-q4` *(experimental)* | 32768 | `q4_0` | 4 blocks |

`--parallel 1` was already enforced: `models.schema.json` pins `parallel` to
`const: 1` and `Assert-V2ManifestSemantics` restates it. No change was needed and
none was made, so the agentic scheduler is untouched.

**Live adapter telemetry.** `cia-edge` reads adapter dedicated and shared memory
through PDH on demand, caches for 2 seconds, and reports on `/api/v1/status` and
`/metrics`. It gates nothing — asserted by a test that fails if the request path
ever samples it.

**Guardrail.** `pressured` requires occupancy ≥ 95% **and** shared ≥ 1024 MiB.
Occupancy alone cannot separate the fastest measured configuration (96.4%) from a
paging one; shared alone fires on any desktop. The floor sits between the healthy
514 MiB case and the degraded 1253 MiB one.

## 4. Before and after

Baseline is the previously recommended configuration: 4-block split, `ub` 512,
KV `q8_0`. New is the shipped workstation default: same split, `ub` 288,
`parallel 1`, KV `q8_0`, context pinned at 32768. Three repetitions each,
`llama-bench`, device isolated to gfx1201.

### Throughput

| | pp512 | pp8192 | pp16384 | pp32768 | tg128 |
|---|---:|---:|---:|---:|---:|
| Baseline `ub` 512 | 299.72 | 289.36 | 268.36 | 239.98 | 23.68 |
| **New `ub` 288** | **956.82** | 269.00 | 249.90 | 222.04 | **23.66** |
| Delta | **+219%** | −7.0% | −6.9% | −7.5% | −0.1% |

Against the stated acceptance criteria: `tg128` is 23.66, above the 22 t/s floor;
the largest prompt-processing regression is 7.5%, inside the 10% tolerance; and
short-prompt prefill triples. Every long-context regression is the same ~7%,
which is the consistent cost of the smaller micro-batch and not a cliff.

### Memory, driver-level

Short-prompt runs (pp512 + pp8192):

| | Dedicated peak | Shared peak | Verdict |
|---|---:|---:|---|
| Baseline `ub` 512 | 15885 MiB | 1330 MiB | pressured |
| **New `ub` 288** | 15938 MiB | **882 MiB** | elevated |
| Delta | +0.3% (noise) | **−34%** | pressured → elevated |

Long-context runs (pp16384 + pp32768):

| | Dedicated peak | Shared peak | Verdict |
|---|---:|---:|---|
| Baseline `ub` 512 | 16057 MiB | 2142 MiB | pressured |
| **New `ub` 288** | **15932 MiB** | **1906 MiB** | pressured |
| Delta | −125 MiB | −236 MiB | unchanged |

Dedicated VRAM is set by the weights and barely moves with `ubatch`. Shared
memory — the paging signal — is what falls, by a third at short prompts. That is
the whole mechanism: it is what took short-prompt prefill from 300 to 957 t/s.
At long context both configurations remain `pressured`, because there the KV
cache rather than the compute buffer is what overflows, and `ubatch` cannot
address it. Context choice can, which is §4's next table.

## 7. Open items

- **Quality evaluation of KV `q4_0` has not been run.** It halves shared memory
  at every context and is a genuine lever, but `docs/MODEL_PROMOTION.md` does not
  allow a cache-precision change on a memory argument alone. It ships as
  experimental and must not be promoted on these numbers.
- **Speculative decoding is untouched**, as instructed. The `blk.64` gate is
  satisfied by the shipped GGUF, so the `spec_draft_n_max` sweep is now
  meaningful; it was not before.
- **Context-checkpoint reuse is unmeasured on this runtime.** ADR 0009's
  addendum and ADR 0010 stand unchanged.
- **The runtime hash pins almost nothing.** `llama-server.exe` in b10549 is a
  9216-byte launcher; the code is in `llama-server-impl.dll` (9988608 bytes,
  `10D214290D1BFA8D93A7E528E2288F0C4DFD3624D31FB44DE030D59852F4DB3C`). The
  pre-existing `unsloth-runtime-candidate` entry has the same weakness. Extending
  the artifact schema to pin a set of files is out of scope here and worth doing.
- **The ROCm runtime is assembled, not shipped.** The official
  `llama-b10549-bin-win-rocm-7.14-x64.zip` contains no rocBLAS closure; these runs
  supply `hipblas/rocblas/rocsolver/libhipblaslt/amd_comgr` and the Tensile tree
  from the pinned ROCm 7.2.1 package. Validated only by a 36/36 correctness pass
  on `GATED_DELTA_NET`. Treat as a stopgap.
- **A documented claim is contradicted.** `model-test-matrix.json` records a 40x
  throughput collapse for `ubatch` in 65..256. Measured here, 256 was the fastest
  configuration at pp512 and level at pp8192. The schema still refuses the band,
  so nothing changes operationally, but the disagreement is recorded in
  TUNING.md 1.6 rather than quietly resolved.

### Memory targets: one met, one not

| Target | Result |
|---|---|
| System RAM ≤ 22–24 GiB | **Borderline.** 26.14 GiB total with the default profile, of which 10.7 GiB is the desktop's own baseline. The model's share is 14.24 GiB. Only `ws-8k-prefill` (25.09) approaches the band. |
| Dedicated VRAM ≤ 15.0 GiB | **Not met, and not reachable at 23 t/s.** The default profile sits at 15.80 GiB. Dedicated VRAM is set by weight placement, not by context or `ubatch`: reaching 15.0 needs roughly 0.9 GiB more weight on the CPU, i.e. a 7-block split, which the measured curve puts at ~17.4 t/s — a 25% decode loss. |

The stated priority order puts "preserve ~23 t/s" above "reduce memory", so the
split was left at 4 blocks and the target is reported unmet rather than met by
sacrificing the thing ranked higher. `ws-8k-prefill` is the one profile that
lands in `ok` (15.36 GiB dedicated, 511 MiB shared) and is available when a
workload genuinely fits in 8k.

## 8. Recommendation

Use **`qwen38-27b-ws-32k`** as the workstation default.

```
-ot "blk\.(6[0-3])\.ffn_.*=CPU"  -ngl 99  -c 32768  -ub 288  -b 2048
-fa 1  -ctk q8_0  -ctv q8_0  -t 8  --parallel 1  --no-context-shift
```

It preserves decode (23.66 t/s against the 23.68 baseline), triples short-prompt
prefill, cuts shared GPU memory by a third, and moves the adapter out of
`pressured` into `elevated` at benchmark load. Switch to `ws-64k` only when a
session genuinely exceeds 32k, and treat `ws-128k` as the high-memory profile it
is labelled.

If the machine needs to be more usable than fast — an IDE, a browser and Unity
alongside — `ws-8k-prefill` is the only profile measured in the `ok` state, and
it is 3.6x faster on prefill below 8k. It loses to the default past 16k.
